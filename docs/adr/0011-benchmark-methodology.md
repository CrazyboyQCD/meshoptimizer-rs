# ADR-0011: Benchmark and memory-measurement methodology versus upstream's scalar profile

- Status: Accepted
- Date: 2026-10-13
- Activates: NFR-11 (previously deferred)
- Builds on: [ADR-0005](0005-c-parity-api.md), [ADR-0007](0007-golden-vectors.md),
  [ADR-0010](0010-scalar-profile-fixtures.md)

## Context

NFR-11 deferred the performance question to a future benchmark suite. Phase 1 is complete and
the suite is now being built, extended with a memory dimension: the comparison must cover both
execution time and allocation behavior (peak allocated bytes, allocation counts), because a
safe-Rust port's most likely regression axis is allocation pattern, not raw compute.

Fairness requirements:

- **Same compiler backend.** rustc and clang both lower to LLVM; using clang (not MSVC) for the
  C++ side removes codegen-backend bias from the comparison. The installed toolchain is clang
  21.1.2 (`x86_64-pc-windows-msvc` target) and a matching-channel rustc.
- **Same execution profile.** Both sides run the scalar profile (`MESHOPTIMIZER_NO_SIMD`,
  [ADR-0010](0010-scalar-profile-fixtures.md)); the Rust crate has no SIMD paths.
- **Upstream output is the oracle.** Timing a wrong implementation is worse than not timing;
  every measured call is output-verified first under the same rules as the golden suite
  (exact bytes/elements/bits everywhere, ≤1 ULP only on the documented `acos`/`log2`/`sin`/`cos`
  paths, TDD §7).
- **Identical inputs.** Both drivers must consume bit-identical input meshes.
- **No third-party tooling.** Neither side pulls in a benchmarking/statistics/serialization
  dependency (no criterion, no Google Benchmark, no serde): the C++ driver uses only the C++
  standard library plus upstream sources; the Rust driver uses only `std` plus the library under
  test (and the library's existing `libm` dependency, untouched).

## Decision

1. **Layout.** The harness lives under `bench/` and is not part of the library crate, the
   workspace gate, or `cargo test`:
   - `bench/cpp/` — `driver.cpp` (upstream sources compiled in) + `build.cmd` (clang).
   - `bench/rust/` — standalone binary crate depending on the library by path; not a workspace
     member, so the root gate is unaffected.
   - `bench/corpus/` — committed corpus *recipes* and hash pins (no large blobs).
   - `bench/results/` — run outputs (JSON + summary), not required to be committed.

2. **Corpus.** Inputs are described by recipes (shape, scale, seed) and generated on the fly by
   both drivers with the same LCG (`0x12345678`, two scale tiers: fixture-scale for the
   correctness gate and a large tier for timing). Each driver hashes its generated inputs
   (FNV-1a 64) and asserts them against the committed pin file; any divergence fails the run
   before anything is timed. Expected outputs for the correctness gate are generated by the C++
   driver (`gen` mode) into a regenerable scratch directory — committed only in hash-pin form,
   never as large blobs.

3. **Memory measurement.** Symmetric counting allocators, enabled per run:
   - Rust: a `GlobalAlloc` wrapper over `System` in the bench binary only; an atomic flag gates
     counter updates (`current` / `peak` / `count`), so `speed` mode pays one untaken branch per
     allocation and `mem` mode records per-call peak.
   - C++: the same shape via upstream's supported `meshopt_setAllocator` hook (counting
     malloc/free forwarders); the library's own allocations are captured without harness noise.
   - Speed runs run with counting **disabled** (raw `System` / pass-through forwarders); memory
     runs are a separate mode and are never used for timing claims.

4. **Timing protocol.** Monotonic clocks (`std::time::Instant` / `std::chrono::steady_clock`),
   warm-up iterations, then an iteration count adaptive to per-call cost (floor of 20), reporting
   median / p95 / min; single-threaded; CPU model, compiler versions, and optimization levels are
   recorded into every results file.

5. **Optimization-level matrix.** Primary comparison: clang `-O2 -DNDEBUG` vs rustc
   `opt-level = 2` (both are the conservative production tier for this code). Secondary
   robustness matrix: `-O3` vs `opt-level = 3`. A gap that only exists on one tier is reported
   as compiler-tier noise, not an implementation gap.

6. **Gap triage.** Ops with time ratio > 1.5× or peak-memory ratio > 1.3× get a written
   attribution (allocation pattern, bounds-check/iterator overhead per disassembly, algorithmic
   divergence). Attribution is analysis-only: the byte-identical port discipline
   ([ADR-0005](0005-c-parity-api.md)) constrains fixes — any optimization must preserve
   upstream-identical output and, if it changes ported structure, goes through an ADR first.

## Consequences

- The bench harness is reproducible from the committed recipes + pins alone; large expected
  outputs are regenerable scratch and never enter version control.
- `bench/rust` is exempt from the library's `[lints]` table by construction (separate crate),
  but follows the same no-`unwrap` house style.
- Timing claims are only made from `speed` mode (counting off); memory claims only from `mem`
  mode. Cross-mode numbers are not comparable and are never mixed in reports.
- The harness measures the scalar profile on one OS/CPU pair; results are informative
  (NFR-11 is not a merge gate) and carry their full environment metadata so reruns elsewhere can
  be compared honestly.
